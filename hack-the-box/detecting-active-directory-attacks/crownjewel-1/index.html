CrownJewel-1

Sherlock Scenario​

Forela's domain controller is under attack. The Domain Administrator account is believed to be compromised, and it is suspected that the threat actor dumped the NTDS.dit database on the DC. We just received an alert of vssadmin being used on the DC, since this is not part of the routine schedule we have good reason to believe that the attacker abused this LOLBIN utility to get the Domain environment's crown jewel. Perform some analysis on provided artifacts for a quick triage and if possible kick the attacker as early as possible.

Preparation​

I began by extracting the provided artifacts. The dataset included essential forensic files for timeline reconstruction:

  • Event Logs: Microsoft-Windows-NTFS.evtx, SECURITY.evtx, and SYSTEM.evtx.

  • File System Metadata: The Master File Table ($MFT)
What is MFT

The $MFT is the heart of the NTFS file system. It acts as an index to all files and directories on the volume, providing metadata like file names, timestamps, and permissions.

Here’s what the MITRE ATT&CK Framework has to say about the technique of dumping the NTDS.dit file (T1003.003):

Adversaries may attempt to access or create a copy of the Active Directory domain database in order to steal credential information, as well as obtain other information about domain members such as devices, users, and access rights. By default, the NTDS file (NTDS.dit) is located in %SystemRoot%\NTDS\Ntds.dit of a domain controller.

In addition to looking for NTDS files on active Domain Controllers, adversaries may search for backups that contain the same or similar information.

The following tools and techniques can be used to enumerate the NTDS file and the contents of the entire Active Directory hashes.

  • Volume Shadow Copy
  • secretsdump.py
  • Using the in-built Windows tool, ntdsutil.exe
  • Invoke-NinjaCopy

Task 1: Tracking the Volume Shadow Copy Service​

Task Description

Attackers can abuse the vssadmin utility to create volume shadow snapshots and then extract sensitive files like NTDS.dit to bypass security mechanisms. Identify the time when the Volume Shadow Copy service entered a running state.

I focused on the System Event Log and filtered for Event ID 7036, which logs service state changes.

I then used the "Find" action to search for the "Shadow" keyword.

Went into Details -> XML View

And found my answer under System -> TimeCreated SystemTime

Task Answer

2024-05-14 03:42:16

Task 2: Identifying the Actor and Privilege Checks​

Task Description

When a volume shadow snapshot is created, the Volume shadow copy service validates the privileges using the Machine account and enumerates User groups. Find the two user groups the volume shadow copy process queries and the machine account that did it.

I pivoted to the Security Event Log and filtered for Event ID 4799 (Security-enabled local group membership enumeration). I specifically looked for activity involving VSSVC.exe around the time the service started.

The logs confirmed that the DC01$ machine account performed the enumeration. The process queried two specific groups to ensure it had the rights to snapshot the drive: Administrators and Backup Operators.

Task Answer

Administrators, Backup Operators, DC01$

Task 3: Mapping the PID​

Task Description

Identify the Process ID (in Decimal) of the volume shadow copy service process.

I saw the PID in the same set of security events.

The log recorded the PID in hexadecimal as 0x1190. Converting it to decimal results in 4496.

Task Answer

4496

Task 4: Extracting the Volume GUID​

Task Description

Find the assigned Volume ID/GUID value to the Shadow copy snapshot when it was mounted.

Once the snapshot is created, it is assigned a unique Volume ID/GUID when mounted. I analyzed the Microsoft-Windows-NTFS logs, looking for events that happened after the timestamp of group enumeration and identified the Volume Correlation ID for the shadow copy.

Task Answer

{06c4a997-cca8-11ed-a90f-000c295644f9}

Task 5: Hunting for the NTDS.dit Dump​

Task Description

Identify the full path of the dumped NTDS database on disk.

To find exactly where the attacker exfiltrated the "crown jewel," I parsed the $MFT file using MFTECmd.exe

And then opened the parsed CSV file in Timeline Explorer and searched for "NTDS.dit".

While standard paths like \Windows\NTDS were present, one location stood out as highly suspicious.

Task Answer

C:\Users\Administrator\Documents\backup_sync_dc\Ntds.dit

Task 6: NTDS.dit Creation Timestamp​

Task Description

When was newly dumped ntds.dit created on disk?

Using the MFT analysis from the previous task, I looked for the exact creation time (Created0x10) of the newly dumped file.

Task Answer

2024-05-14 03:44:22

Task 7: Missing Link: The SYSTEM Hive​

Task Description

A registry hive was also dumped alongside the NTDS database. Which registry hive was dumped and what is its file size in bytes?

An NTDS.dit file is unusable without the SYSTEM registry hive, which contains the boot key needed to decrypt the database hashes. I searched the MFT results for the suspicious backup_sync_dc parent path to see what else was staged in that directory.

There it is, I found the SYSTEM hive sitting right next to the database.

Task Answer

SYSTEM, 17563648
